# Linux RAG Agent 项目开发指南

> 用途：统一三人小组对项目目标、系统边界、模块分工、开发顺序和验收标准的认识。  
> 开发原则：先完成可运行的最小闭环，再逐步替换为真实服务；先保证正确性，再进行并发和性能优化。

## 项目目标

本项目要基于C++实现一个运行在 Linux 上、支持多个客户端同时访问的 RAG Agent。用户通过命令行客户端向 Agent 发送请求，Agent 根据请求类型完成普通对话、本地知识库问答或受控的 Linux 命令执行，并将结果返回客户端。

本项目不是训练大模型，也不是从零实现向量数据库或神经网络。课程开发重点是：

- Linux Socket 与 `epoll` 网络编程；
- 固定工作线程池、有界任务队列和并发控制；
- 进程、管道、信号和子进程回收；
- C++ 服务与 Python/现成服务之间的 HTTP、JSON 通信；
- RAG 检索流程的组织；
- 命令执行的白名单、超时和资源限制；
- 多客户端环境下的正确性、稳定性和过载处理。

系统最终支持三类请求：

|类型|含义|处理路径|
|---|---|---|
|`CHAT`|普通知识问答|Agent → 大模型|
|`RAG`|根据本地资料回答|Agent → 检索服务 → 大模型|
|`CMD`|执行允许的 Linux 操作|Agent → 安全检查 → 子进程执行|

第一版由客户端明确指定请求类型，例如 `/chat`、`/rag` 和 `/cmd`。暂不使用大模型自动判断用户意图。

## 项目边界

### 小组需要实现的部分

- C++ 命令行客户端；
- C++ Agent 服务器；
- TCP 应用层消息协议；
- 非阻塞 Socket 与单 `epoll` 网络线程；
- 固定大小工作线程池；
- 有界任务队列、完成队列和过载处理；
- 请求路由与一次请求的生命周期管理；
- RAG 服务调用和 Prompt 构造；
- 安全命令执行器；
- 文档导入工具或脚本；
- 多客户端测试脚本、日志和实验报告。

### 使用现成组件的部分

- Embedding 模型；
- Qdrant 向量数据库；
- `llama-server`；
- Qwen 等预训练大模型；
- JSON、HTTP等基础库。

### 第一版暂不实现

- 训练或微调大模型；
- Web 前端；
- 多轮长期记忆；
- 自动工具规划；
- 流式 Token 返回；
- 动态线程池、无锁队列和内存池；
- 分布式向量数据库；
- 1000 个真实大模型请求同时推理；
- 允许用户执行任意 Shell 命令。

## 命令行客户端交互方案

正式客户端采用交互式命令行（REPL）形式，使用体验接近常见的大模型CLI。`curl`只用于单独调试RAG、Qdrant和LLM等HTTP服务，不作为最终用户访问Agent的主要方式。

推荐将可执行程序命名为：

```Plain Text
agent-server    Agent服务端
agent           交互式客户端
```

启动客户端并连接服务器：

```Bash
./agent --host 127.0.0.1 --port 9000
```

连接成功后，希望显示：

```Plain Text
_____            _____             _
 |  __ \     /\   / ____|           | |
 | |__) |   /  \ | |  __  ___ _ __  | |_
 |  _  /   / /\ \| | |_ |/ _ \ '_ \ | __|
 | | \ \  / ____ \ |__| |  __/ | | || |_
 |_|  \_\/_/    \_\_____|\___|_| |_| \__|

RAG Agent CLI
Connected to 127.0.0.1:9000

输入 / 查看可用命令，输入 /help 查看帮助。
agent>
```

### 三种交互模式

客户端具有四种本地状态：

```C++
enum class ClientMode {
    MAIN,
    CHAT,
    RAG,
    CMD
};
```

主界面只负责选择模式或执行单次请求。进入模式后，提示符随之变化：

```Plain Text
agent> /chat
已进入 CHAT 模式，输入 /back 返回主界面。
chat> 什么是TCP？

chat> /back
agent> /rag
已进入 RAG 模式，输入 /back 返回主界面。
rag> 本实验为什么使用epoll？

rag> /back
agent> /cmd
已进入 CMD 模式，输入 /list 查看允许的操作。
cmd> 查看磁盘空间

cmd> /back
agent> /exit
```

模式只用于决定客户端发送的请求类型。服务器仍通过每条消息中的`type`字段识别CHAT、RAG或CMD，不依赖客户端之前发送过“进入模式”消息。

### 命令与退出规则

第一版统一支持以下命令：

|命令|作用|
|---|---|
|`/chat [问题]`|进入CHAT模式，或完成一次CHAT请求|
|`/rag [问题]`|进入RAG模式，或完成一次RAG请求|
|`/cmd [操作]`|进入CMD模式，或完成一次CMD请求|
|`/back`|退出当前模式，返回`agent>`主界面|
|`/help`|显示当前可用命令及说明|
|`/status`|查询Agent及依赖服务状态|
|`/clear`|清理终端显示|
|`/exit`|断开连接并退出整个客户端|
|`/list`|在CMD模式中显示允许的操作|

退出语义必须保持一致：

- `/back`只退出CHAT、RAG或CMD模式；
- `/exit`始终退出整个客户端；
- `Ctrl+`C可以等价于`/exit`；

### Enter、Tab与单次请求

`Enter`用于确认并执行当前输入，`Tab`只用于补全和展示候选命令。

```Plain Text
agent> /r<Tab>
agent> /rag
```

当输入`/`后按Tab，因为存在多个候选项，客户端显示命令及解释：

```Plain Text
/chat    普通大模型对话
/rag     根据本地知识库回答
/cmd     执行允许的Linux系统操作
/help    查看帮助
/exit    退出客户端
```

无参数命令进入对应模式：

```Plain Text
agent> /rag
rag>
```

带参数命令完成一次请求，但不进入模式：

```Plain Text
agent> /rag 什么是epoll？
……回答……
agent>
```

模式内的普通文本按当前模式发送：

```Plain Text
chat> 解释一下线程池     → type=CHAT
rag> 项目如何部署？      → type=RAG
cmd> 查看内存            → type=CMD
```

在`MAIN`状态直接输入普通文本时，第一版应提示用户先选择模式，不默认猜测请求类型。

### 客户端的两种运行方式

客户端必须同时支持人工交互和自动化测试。

交互模式用于日常操作和课程演示：

```Bash
./agent --host 127.0.0.1 --port 9000
```

单次请求模式用于Shell脚本和多客户端测试：

```Bash
./agent \
  --host 127.0.0.1 \
  --port 9000 \
  --mode rag \
  --query "什么是epoll？"
```

两种模式共用连接、消息编解码、请求发送和响应解析代码，不能分别实现两套协议逻辑。

### 分级实现

交互界面建议按照以下顺序开发：

1. 使用`std::getline`完成输入循环、模式切换和斜杠命令；
2. 接入真实TCP连接、消息协议和服务端响应；
3. 增加Logo、颜色、`/help`和命令说明；
4. 使用GNU Readline等库增加上下键历史记录；
5. 增加Tab命令补全；
6. 增加单次请求参数模式和脚本化退出码。

第一版不实现全屏TUI、鼠标操作、固定聊天窗口和复杂终端刷新。若使用GNU Readline，命令帮助、命令解析和Tab补全应共用同一张命令定义表，避免三处分别维护命令名称。

## Agent 内部并发结构

采用保守、易于学习和调试的结构：

```Plain Text
单 epoll 网络线程 + 全局固定工作线程池
```

```Plain Text
flowchart TD
    A[epoll_wait] --> B[接受连接/读取字节]
    B --> C[连接缓冲区与协议解码]
    C --> D{消息是否合法}
    D -->|否| E[生成协议错误或关闭连接]
    D -->|是| F[创建 Request]
    F --> G{任务队列是否已满}
    G -->|是| H[返回 SERVER_BUSY]
    G -->|否| I[写入有界任务队列]
    I --> J[工作线程取任务]
    J --> K[CHAT / RAG / CMD 处理]
    K --> L[写入完成队列]
    L --> M[eventfd 唤醒网络线程]
    M --> N[网络线程找到对应连接]
    N --> O[加入连接发送缓冲区]
    O --> P[EPOLLOUT 发送响应]
```

线程职责必须保持清楚：

### epoll 网络线程

- 接受新连接；
- 非阻塞读取和写入；
- 处理半包、粘包；
- 管理连接状态与收发缓冲区；
- 将完整请求放入任务队列；
- 从完成队列取回响应；
- 处理断开、协议错误和发送失败。

网络线程不得执行Embedding、Qdrant查询、LLM调用或耗时命令。

### 工作线程

- 从任务队列取出请求；
- 按类型执行CHAT、RAG或CMD处理；
- 调用外部HTTP服务；
- 构造统一响应；
- 将响应放入完成队列；
- 通过`eventfd`通知网络线程。

工作线程第一版不得直接向客户端Socket发送数据，Socket写入由网络线程统一管理。

### 必需的队列

|队列|生产者|消费者|是否有界|
|---|---|---|---|
|任务队列|网络线程|工作线程|是|
|完成队列|工作线程|网络线程|是，或具有全局结果内存上限|
|每连接发送缓冲区|网络线程|网络线程|是，限制单连接待发送字节数|

LLM并发还需要单独限制。即使工作线程有4个，也建议真实LLM推理并发先设为1，其余请求在有界条件下等待，避免占满GPU和内存。

## 一次请求的完整流程

### RAG请求

```Plain Text
客户端指定 /rag 并输入问题
→ Agent接收并解析消息
→ 请求进入任务队列
→ 工作线程调用RAG服务
→ RAG服务将问题转为向量
→ Qdrant返回Top-K相关文本块
→ Agent构造“资料 + 问题”Prompt
→ Agent调用llama-server
→ 工作线程生成响应
→ 网络线程将响应发给原客户端
```

### CHAT请求

```Plain Text
客户端指定 /chat
→ 请求进入线程池
→ 工作线程直接构造普通对话Prompt
→ 调用llama-server
→ 返回回答
```

### CMD请求

```Plain Text
客户端指定 /cmd
→ 工作线程识别预定义操作
→ 检查命令和参数白名单
→ fork创建子进程
→ exec执行确定的程序和参数
→ pipe捕获stdout/stderr
→ 检查超时与输出上限
→ waitpid回收子进程
→ 返回执行结果
```

禁止将用户原始字符串交给`system()`或`/bin/sh -c`。

## 分阶段开发计划

每个阶段都必须形成可编译、可运行、可演示的版本。上一阶段没有通过验收，不应同时引入下一阶段的复杂度。

### 阶段0：需求与接口冻结

目标：三个人对“做什么、暂时不做什么、如何连接”形成一致认识。

任务：

- 确认三类请求及处理边界；
- 确认总体部署方案；
- 确认模块负责人；
- 确认目录结构和命名规范；
- 定义协议头、请求类型、响应状态和错误码；
- 定义RAG服务、LLM服务和命令执行器接口；
- 准备Git仓库、CMake和基础CI/检查命令。

阶段产物：

- 项目需求与范围说明；
- 架构图；
- 协议文档；
- 模块接口文档；
- 分工与开发计划；
- 可以编译的空项目骨架。

验收标准：

- 每名成员都能口头说明一次RAG请求的完整路径；
- 公共数据结构没有明显冲突；
- 所有人可以在自己的环境中拉取并编译项目。

### 阶段1：单客户端网络最小闭环

目标：实现最简单的客户端与服务器通信，不加入线程池和AI服务。

任务：

- 完成TCP客户端；
- 使用`std::getline`实现交互循环和`agent>`提示符；
- 实现`/chat`、`/rag`、`/cmd`、`/back`、`/help`和`/exit`；
- 实现交互模式和单次请求模式；
- 完成监听、连接和基础`epoll`循环；
- 完成长度前缀消息协议；
- 完成收包缓冲区、半包和粘包处理；
- 服务器返回固定响应；
- 输出连接和请求日志。

演示路径：

```Plain Text
客户端发送 hello → 服务器返回 server received: hello
```

验收标准：

- 客户端可以连续发送多条消息；
- 三种模式的进入、返回和退出语义正确；
- 单次请求模式可以被Shell脚本调用并返回有效退出码；
- 消息拆分发送仍能正确解析；
- 非法长度被拒绝；
- 客户端断开后服务器继续运行；
- 请求和响应具有相同的`request_id`。

### 阶段2：多客户端与固定线程池

目标：建立正式的并发骨架。

任务：

- 实现固定工作线程池；
- 实现有界任务队列；
- 定义`Request`和`Response`；
- 实现完成队列；
- 使用`eventfd`唤醒网络线程；
- 实现队列满时的`SERVER_BUSY`；
- 增加测试用慢任务；
- 编写10客户端并发脚本。

验收标准：

- 10个客户端能够同时保持连接；
- 4个工作线程处理10个5秒任务时呈批次完成；
- 网络线程在慢任务期间仍能接受新连接；
- 队列满时不会无限占用内存；
- 客户端提前断开不会导致崩溃或结果串线；
- 服务器能够有序停止并回收线程。

### 阶段3：Mock Agent完整闭环

目标：在不依赖真实模型和数据库的情况下跑通三条业务路径。

任务：

- 实现CHAT、RAG、CMD请求路由；
- 实现Mock RAG服务；
- 实现Mock LLM服务；
- 实现Mock命令执行结果；
- 统一成功和失败响应格式；
- 加入外部服务超时和错误映射；
- 完成端到端测试。

验收标准：

- 三类请求都能得到可预测响应；
- 每条失败路径都有明确错误码；
- Agent的网络、线程和业务模块可以独立测试；
- 关闭Mock服务时Agent不会崩溃。

### 阶段4：真实RAG检索

目标：完成本地文档到检索结果的闭环，暂时可以不调用真实大模型。

任务：

- 部署Qdrant；
- 部署轻量Embedding服务；
- 编写文档读取、清洗和分块程序；
- 保存文本、来源、块编号和向量；
- 实现`/retrieve`接口；
- 返回Top-K文本块、来源和分数；
- 准备小规模知识文档和标准问题集。

验收标准：

- 文档只需导入一次即可重复查询；
- 已知问题能检索到正确文本块；
- 检索结果保留来源信息；
- 无结果、Embedding失败、Qdrant不可用均有清晰响应；
- 重复导入不会无控制地产生重复数据。

### 阶段5：真实大模型与完整RAG

目标：使用Windows宿主机上的`llama-server`完成真实回答。

任务：

- Windows部署Qwen量化模型；
- 打通Ubuntu虚拟机到Windows模型服务的网络；
- C++ Agent实现LLM HTTP/JSON客户端；
- 构造普通对话Prompt和RAG Prompt；
- 设置请求超时、输出长度和LLM并发上限；
- 在回答中返回或展示资料来源。

验收标准：

- CHAT能够获得真实模型回答；
- RAG回答能够使用检索资料；
- 资料不足时明确说明，不凭空补充内部事实；
- 模型不可用或超时时Agent仍保持运行；
- 真实LLM并发受控，等待请求不会无限增长。

### 阶段6：安全命令执行

目标：安全执行少量预定义Linux操作。

任务：

- 建立命令和参数白名单；
- 实现`fork/exec/pipe/dup2/waitpid`；
- 捕获标准输出和标准错误；
- 实现执行超时、输出长度上限和子进程回收；
- 拒绝Shell元字符和任意程序路径；
- 根据时间允许再加入seccomp、cgroups等限制。

第一批可以支持：

```Plain Text
pwd
date
uname -a
df -h
free -h
```

验收标准：

- 白名单操作执行成功；
- 非白名单命令和非法参数被拒绝；
- `;`、`&&`、管道等无法拼接命令；
- 超时子进程会被终止并回收；
- 大量输出不会耗尽服务器内存。

### 阶段7：集成、故障和并发测试

目标：验证系统在正常、异常和并发情况下的行为，并形成可复现实验数据。

任务：

- 单客户端连续请求测试；
- 10客户端同时连接和请求测试；
- 半包、粘包、非法消息和突然断开测试；
- 队列满和`SERVER_BUSY`测试；
- RAG、Qdrant、LLM服务停机测试；
- 命令超时和输出过大测试；
- 服务器启动、运行和关闭测试；
- 收集成功率、队列等待时间、处理时间和总延迟。

并发测试分开进行：

- 使用真实模型验证完整功能和低并发请求；
- 使用Mock模型测试大量TCP连接、任务队列和过载策略；
- 不将大量网络连接等同于大量真实模型同时推理。

验收标准：

- 请求不丢失、不重复、不串到其他连接；
- 所有已接受任务都有成功或失败的终态；
- 外部服务故障不会导致Agent整体退出；
- 日志足以定位一次请求经过的阶段；
- 测试结果可通过脚本重复获得。

## 公共接口冻结顺序

不要先把所有头文件一次性设计完成。推荐按照依赖关系逐层冻结：

```Plain Text
消息协议
→ Request/Response
→ 连接与任务的所有权
→ 线程池接口
→ 业务处理器接口
→ RAG/LLM HTTP接口
→ 配置和日志字段
```

每个接口先回答四个问题：

1. 输入是什么？
2. 输出是什么？
3. 谁创建、谁持有、谁释放？
4. 失败时如何表示？

头文件只声明稳定的公共类型和函数，不把模块内部细节全部暴露出去。公共头文件发生不兼容修改前，需要三人共同确认。

## 日志与可观测性

服务器日志至少包含：

```Plain Text
时间
日志级别
connection_id
request_id
请求类型
当前阶段
worker_id
队列等待时间
处理时间
总时间
最终状态
错误原因
```

示例：

```Plain Text
[INFO] conn=12 req=1008 type=RAG worker=2 queue_ms=18 process_ms=2340 status=OK
```

日志不得记录密码、Token、完整敏感文档或未经控制的超长模型输出。
