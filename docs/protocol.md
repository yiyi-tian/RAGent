# RAGent TCP协议规范 v1

状态：协议约定已由项目方确认，v1作为第一阶段实现依据。基础TCP编解码、固定响应和PING/PONG已实现；后续业务错误码与服务能力按开发阶段接入。不兼容修改需要重新确认。

## 1. 范围与原则

客户端和Agent使用TCP长连接，采用固定二进制消息头和UTF-8 JSON消息体。TCP是字节流，一次读取不等于一条消息；接收端必须处理半包、粘包，发送端必须处理部分写入。

消息头确定边界、类型和请求标识，JSON表达业务数据。客户端模式只影响当前输入对应的请求类型，服务器不保存客户端的CHAT/RAG/CMD模式。

第一版不包含身份认证、TLS、流式输出、取消请求、断线续传和自动重试，部署于受控课程实验网络。

## 2. 消息头与帧边界

```text
固定20字节消息头 | body_length字节JSON消息体
```

| 偏移 | 字段 | 无符号整数宽度 | 约定 |
|---|---|---|---|
| 0 | magic | 32位 | 0x52414754，ASCII为RAGT |
| 4 | version | 16位 | 1 |
| 6 | message_type | 16位 | 见消息类型表 |
| 8 | body_length | 32位 | JSON编码后的字节数 |
| 12 | request_id | 64位 | 请求标识，响应原样返回 |

所有整数使用大端序（网络字节序），包括64位request_id。按偏移逐字段编码和解码，不直接收发C++结构体内存，也不以sizeof结构体计算线上头长度。

消息体最多1 MiB，即1,048,576字节；限制对两个方向均有效。收到完整头后先校验magic、version和长度，再等待或分配消息体。长度为0时消息边界有效，但消息体不是合法JSON对象，按INVALID_REQUEST处理。

### 编码样例

CHAT_REQUEST、request_id=1、消息体为无换行的`{"query":"hello"}`，消息体长度为17字节，其头部应为：

```text
52 41 47 54  00 01  00 01  00 00 00 11  00 00 00 00 00 00 00 01
```

头部后紧接17字节消息体，不添加分隔符、NUL或额外换行。JSON内部空白合法，但实际发送的空白也必须计入body_length。中文按UTF-8字节数计算，不能使用字符数。

## 3. 消息类型与JSON约定

| 类型 | 编号 | 方向 | 含义 |
|---|---|---|---|
| CHAT_REQUEST | 1 | 客户端→Agent | 普通对话 |
| RAG_REQUEST | 2 | 客户端→Agent | 本地知识库问答 |
| CMD_REQUEST | 3 | 客户端→Agent | 受控操作 |
| RESPONSE | 100 | Agent→客户端 | 业务成功 |
| ERROR | 101 | Agent→客户端 | 请求失败 |
| PING | 200 | 客户端→Agent | 网络存活检查 |
| PONG | 201 | Agent→客户端 | PING响应 |

消息体必须是合法UTF-8 JSON对象，不包含BOM或尾随非空白数据。业务类型只由头部决定，不在JSON中重复放type。字段类型必须准确，不将数字自动转换为字符串。未知字段忽略；改变字段含义或新增必填字段属于不兼容修改，需要升级版本。

### 业务请求

CHAT_REQUEST、RAG_REQUEST、CMD_REQUEST共用：

```json
{
  "query":"什么是 epoll？"
}
```

query必须是非空白字符串；判空白至少覆盖空格、制表符、回车和换行。判空不代表修改原始query。不传用户身份、多轮历史或模型参数。

### 成功响应

RESPONSE统一包含text字符串和sources数组：

```json
{
  "text":"epoll 是 Linux 提供的 I/O 事件通知机制。",
  "sources":[]
}
```

CHAT、CMD及第一阶段固定响应的sources为空。RAG来源项约定如下：

```json
{
  "text": "项目使用单 epoll 网络线程处理连接与非阻塞收发。",
  "sources": [
    {
      "source": "development-plan.md",
      "chunk_id": "chunk-12",
      "text": "采用单 epoll 网络线程 + 全局固定工作线程池。",
      "score": 0.86
    }
  ]
}
```

source、chunk_id、text均为字符串，score为有限JSON数值，表示检索相关性，不解释为概率。source使用可展示的文档标识，不暴露服务器私有绝对路径。

第一阶段三类请求均返回固定模板，不调用真实服务或执行命令。例如query为hello时：

```json
{
  "text":"server received: hello",
  "sources":[]
}
```

编码后的响应也必须满足1 MiB限制。不能截断已编码JSON；结果过大且业务层未预先限制时，返回小体积INTERNAL_ERROR。CMD输出超限使用专用错误码。

### 错误响应

ERROR统一为：

```json
{
  "code":"SERVER_BUSY",
  "message":"任务队列已满，请稍后重试。"
}
```

code用于程序判断，message用于展示，不应解析message文字；message不能包含密钥、私有堆栈或未经限制的外部服务输出。

| code | 含义 |
|---|---|
| INVALID_REQUEST | JSON、必填字段或字段类型非法 |
| UNSUPPORTED_MESSAGE_TYPE | 消息类型未知或方向不合法 |
| SERVER_BUSY | 有界容量已满，请求未接纳 |
| UPSTREAM_UNAVAILABLE | 外部服务不可连接或返回失败 |
| UPSTREAM_TIMEOUT | 外部服务调用超时 |
| COMMAND_NOT_ALLOWED | 操作或参数不在白名单内 |
| COMMAND_TIMEOUT | 命令执行超时 |
| COMMAND_OUTPUT_LIMIT | 命令输出超限 |
| COMMAND_FAILED | 命令启动失败或非零状态退出 |
| INTERNAL_ERROR | Agent内部处理失败 |

各阶段仅实现已接入能力对应的错误码。错误与成功响应均回显原请求request_id。

### PING/PONG

两者消息体均为`{}`。PING由网络线程直接处理，不进入业务任务队列；PONG回显request_id。PONG只表示Agent网络循环能响应，不代表RAG、Qdrant或LLM健康。

`/status`依赖健康检查和`/list`操作列表尚无独立线上消息类型，后续实现时另行明确；不能把PONG当成所有服务健康，也不能将本地模式切换发送成业务请求。

## 4. 请求生命周期

request_id从1开始，在同一连接中随请求（包括PING）递增且不复用；重连可从1重新开始。服务器遇到0或不递增的ID时关闭连接并记录协议错误，避免重复ID产生歧义。64位ID耗尽前客户端应重建连接。

同一连接允许多个在途请求，响应不保证请求顺序。客户端通过request_id匹配；第一版CLI一次仅发送并等待一个请求。客户端收到无对应在途请求的响应或非法服务端帧时，将连接视为异常并关闭。

对合法请求，服务器生成一个终态结果：业务请求为RESPONSE或ERROR，PING为PONG或请求校验错误。连接可用时尝试发送；断开或发送失败后不保证送达，不跨连接补发。消息格式错误且边界可信时返回ERROR；无法信任消息头时直接关闭。

客户端默认不自动重试。等待超时不代表服务端已经停止；尤其不能据此重发CMD。request_id用于匹配，不提供业务去重或恰好一次执行保证。客户端响应等待超时后关闭连接，并报告结果未知。

## 5. 解码、错误和资源行为

接收循环累计字节，头不足20字节则等待；头合法且消息体未齐则等待；完整帧到达后消费它，再继续解析缓冲区中的下一帧。不要等待下一次可读事件才处理已完整的后续帧。

| 情况 | 行为 |
|---|---|
| magic错误、version不支持、长度超限 | 立即关闭，不搜索下一个magic重新同步 |
| 消息边界有效，JSON或字段错误 | 返回INVALID_REQUEST，继续使用连接 |
| 消息边界有效，类型未知或方向非法 | 返回UNSUPPORTED_MESSAGE_TYPE，继续使用连接 |
| EOF且残留不完整帧 | 丢弃残留，记录原因并清理连接 |
| EOF、连接重置、不可恢复读写错误 | 清理连接，迟到结果丢弃 |
| 任务队列满 | 返回SERVER_BUSY，不入队 |
| 接收或发送缓冲达到上限且无法继续容纳数据 | 关闭连接并记录资源限制原因 |

不承诺支持TCP半关闭：客户端发送完请求后必须保持连接可读写，直到收到结果。

接收端须增量消费合法数据，避免把“单次读到多个合法帧”误当成单帧超限。每连接收发缓冲、任务队列和完成结果内存均须有界；具体容量与等待超时为实现阶段配置，不能无限堆积。发送时保留尚未写出的字节，仅在有待发送数据时关注EPOLLOUT。

## 6. 验收场景

第一阶段：

- 使用上述字节样例验证头部编码；再使用非零高32位request_id验证64位大端序。
- 验证中文长度、空消息体、非对象JSON、无效UTF-8、缺字段、错类型和空白query。
- 按任意位置拆分头与体，并把多帧合并发送，确认连续解析且ID正确。
- 验证1 MiB长度边界、超限头、错误magic/version、未知类型、非法方向和重复ID。
- 模拟部分写入与中途断开，确认数据不丢、服务器继续运行。
- 验证三种模式和单次请求共用编解码，固定响应与PING/PONG符合约定。

第二阶段：

- 同一连接多个任务乱序完成，客户端按ID匹配。
- 验证任务队列满时SERVER_BUSY及慢客户端触发发送上限。
- 客户端断开后新连接复用同一fd，旧任务结果不能发送给新连接。
- 验证完成结果内存有界及有序停止；日志能解释未送达结果的原因。

第一阶段已提供黑盒自动化测试，运行方式和覆盖范围见[验证说明](testing.md)。第二阶段条目保留为后续验收要求，尚未实现线程池或任务队列。
