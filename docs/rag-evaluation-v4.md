## 为什么采用两种粒度

只按段落检索容易把多个选项混在一起；单独按条目检索又损失概述、名称和完整说明。
本轮的条目方案虽使原验证集达到 8/8，却使开发集降到 17/23，因此没有单独发布。
最终保留两种粒度：

- 段落块覆盖概述、连续说明和状态表。
- 条目块按缩进、选项和子命令边界拆分；后续段落的索引文本保留所属条目的标题。
- 条目通过同一来源、文档哈希及原文区间的最大重合，关联到段落块。

每次请求只生成一次查询向量，然后分别查询两种粒度各前 20 条。排名以
`1 / (10 + 段落排名) + 0.5 / (10 + 条目排名)` 融合；一个段落只接受排名最靠前的
相关条目的一票，防止条目多的章节占优；未进入某一路候选时，该路计 0。参数只按开发集选择，未对验证题添加答案规则。
这增加一次本地 Qdrant 向量查询，不增加在线大模型调用次数，也不新增 Python 依赖。

最终返回最多 5 条证据。优先补齐同来源、同章节的上下文；若命中条目的开头与说明
相距较远，只补充通过原文位置关联的条目开头，省略位置以 `[…]` 标记。
不把无关检索结果拼成一个块来提高覆盖。正文上限仍为 1800 字符，锚点 `chunk_id`
和所含 `context_chunk_ids` 可追踪。不同来源即使文档哈希相同，也不共享上下文。

多粒度结果的 `score` 是排名融合相关性分数；单路向量分数仍是余弦相似度。
两者不可直接比较，也不解释为概率。TCP 和内部 HTTP 字段保持兼容。

## 回答和运行验证

固定八题完成双版本真实 DeepSeek 回答对比，共 16 次调用，包括 grep 退出码、grep
反选、失败单元筛选、开机启动、目录自身信息、用户级服务管理器，以及 Docker 构建和
curl 超时两个证据不足问题。人工复核的六个正例回答均有相关证据支持，候选对开机启动
同时给出了语法、效果及 enable/start 区别；两个负例没有被补全成操作步骤。
该有限样本未发现严重新增无依据结论，不代表模型对所有问法都有同等表现。

真实 C 客户端 → C 服务 → Python Agent → Embedding → Qdrant → DeepSeek 的
RAG、AGENT 两条链路通过：RAG 正确说明失败单元筛选，AGENT 调用检索并正确解释
`grep -v`。这两条请求使用 3 次模型调用。默认配置的独立检索和日常启动也完成验证。

单次本地融合处理平均约 5.3 ms，索引构建约 2–3 秒；这只是本轮 92 题的观测，
不代表包含云端模型、并发排队的端到端延迟。新方案端到端实测见
[并发配置与测量](performance-concurrency.md)。索引在启动时构建、运行时只读，入库后
需重启 Python 服务；不支持自动刷新。

本轮累计 Embedding **102 次 HTTP 请求、975 条文本**，DeepSeek **19 次调用**，
低于 150 次、1200 条、20 次上限。段落向量直接复用，948 个新条目单独生成向量，
没有为融合方案重新付费生成整库向量。失败也计入预算，无自动重试。

## 使用与回退

本机 `.env`、`.env.example`、Python 默认配置和导入默认规则已同步。
日常启动仍为：

```bash
bash scripts/start.sh
```

已有本机数据无需再次入库。新机器按 [README](../README.md) 首次部署，默认同时生成
段落及条目块；实际数量取决于安装的手册语言与发行包版本。旧 `.env` 不会被部署脚本
覆盖，其他成员升级时应将集合设为 `linux_manual_v4`、策略设为 `context`，再向新集合
导入或恢复对应数据；不要向旧集合混合导入。常规导入会调用 Embedding。

若需回退本机检索，在 `.env` 将 `RAGENT_QDRANT_COLLECTION` 改回 `linux_manual_v1`、
`RAGENT_RETRIEVAL_STRATEGY` 改为 `vector`，重启 Python 服务即可，不需重新入库。
再次向旧集合导入必须显式使用 `--chunking v1`，且来源内容和版本必须一致。
